## Evidence-informed recommendation (proposal)

After the initial research, the user supplied module and filtered file-path listings from both actual initramfs archives. Both show systemd, ZFS, `dracut-zfs-generator`, `zfs-env-bootfs.service`, `zfs-nonroot-necessities.service`, snapshot/rollback services, embedded `20-root-dev.conf`, and `zpool.cache`. The supplied filtered listings show neither host `zfs-mount-generator` nor `zfs-list.cache`. Musashi's archive lists its existing key file with mode `0600`; no key contents were requested or read. These are archive-membership observations, not verification of script contents or successful alternate boot.

**Recommend candidate A for v1, subject to acceptance testing:** persistent filtered caches per environment, produced exclusively by loka, with synchronous refresh and validation before a clone, rename, or rollback is considered bootable. The user accepts explicit refresh/validation after external topology or property changes. Together with the observed initrd layout, this makes retaining the stock host generator a smaller integration than introducing a root-aware generator. There is currently no evidence requiring per-boot initramfs cache refresh. Candidate B remains a fallback if acceptance exposes a requirement that persistent-cache ownership cannot satisfy.

This proposal includes disabling the stock whole-pool cache ZEDLET for managed caches and eliminating the automatic global `zfs mount -a` bypass. Retain shared mounts and their dependencies, including external encryption-root rows; exclude other environments' private rows even when those environments are ineligible for loka. Generate required activation for selected `noauto` mounts and preserve `off` containers without mounting them. Clone/rename/rollback publication must follow cache repair, including repair after rollback restores old cache files. Shared topology changes may invalidate several offline environments, so explicit refresh must cover all affected environments.

Read-only inspection of the first target's installed dracut units found that snapshot and rollback services require respectively `ConditionKernelCommandLine=bootfs.snapshot` and `ConditionKernelCommandLine=bootfs.rollback`, plus `ConditionEnvironment=BOOTFS`. Merely including the units does not activate these operations. Their commands operate on the root dataset, not a coordinated recursive environment; these command-line recovery options should therefore be excluded from loka's supported whole-environment workflow. Installed evidence: `/usr/lib/dracut/modules.d/90zfs/zfs-{snapshot,rollback}-bootfs.service`. This does not prove archive contents match installed files.

The installed `zfs-env-bootfs.service` decodes explicit root selection and consults pool `bootfs` only for `zfs:AUTO`. Dracut 112 combines embedded command-line files before `/proc/cmdline`, followed by runtime initramfs command-line files. A harmless synthetic invocation of the installed argument parser confirmed that its last `root=` wins: an actual selected-root argument overrides an embedded default, while a later runtime override could supersede it. Thus the presence of `20-root-dev.conf` alone does not establish a clone boot bug. Its unseen contents and runtime overrides remain acceptance inputs. [Dracut 112 command-line composition](https://github.com/dracut-ng/dracut-ng/blob/112/modules.d/80base/dracut-lib.sh#L123). Local sources: `/usr/lib/dracut/modules.d/80base/dracut-lib.sh`, `/usr/lib/dracut/modules.d/90zfs/zfs-env-bootfs.service`, and `/usr/lib/dracut/dracut-util`.

The remaining gate is behavioral acceptance, not another broad privileged inventory: directly boot an alternate clone, verify selected root and every required private mount, retain shared mounts, exclude foreign private members, and repeat after rename and rollback. Verify reload, external-change refresh, encrypted unlock using existing credentials, required-mount failure behavior, and absence of the global mounting bypass. Test ordinary boots without root-only snapshot/rollback options. No boot test has yet established these outcomes.

## Upstream constraints

The stock generator reads `/etc/zfs/zfs-list.cache/<pool>`. Cache rows name datasets explicitly; mount-unit names derive from mountpoints. Duplicate `noauto` mountpoints suppress their units; `on` rows take precedence. `canmount=off` suppresses mounting, while `noauto` needs an explicit activation dependency. `org.openzfs.systemd:required-by` is one supported way to supply one. Filtering therefore has to occur **before** collisions discard rows. [OpenZFS generator manual](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-mount-generator.8.html).

The enabled stock ZED cacher rewrites the entire pool after create, receive, import, destroy, rename, and tracked property changes; export empties its cache. It updates the running installation's path, not every offline environment. An environment-filtered cache cannot share ownership with this writer. Replacing the writer, or disabling that ZEDLET while retaining other ZED functionality, requires an explicit refresh owner and completion check. [Upstream cacher source](https://github.com/openzfs/zfs/blob/master/cmd/zed/zed.d/history_event-zfs-list-cacher.sh.in). The first target's installed cacher was also read and has these behaviors.

Encryption-root rows matter even when outside the selected subtree: the generator emits a key-loading service when processing the encryption root's own row, before testing `canmount` or `ignore`. Encrypted descendant units depend on that service. Thus Musashi's filtered input must retain `rpool` metadata despite its `canmount=off`, alongside eligible shared mounts. Selecting only the environment subtree would be incomplete. [Generator source, `line_worker`](https://github.com/openzfs/zfs/blob/master/etc/systemd/system-generators/zfs-mount-generator.c#L256).

Systemd generators run before unit loading, execute in parallel, and run again on manager reload. They have a mostly read-only sandbox and may write only their output locations; a separate generator cannot be ordered to rewrite the cache before the stock generator. Host-side generators can inspect `/proc`; initrd and host invocations are distinguishable through `SYSTEMD_IN_INITRD` on the inspected systemd generation. [systemd 261 generator contract](https://github.com/systemd/systemd/blob/v261/man/systemd.generator.xml).

The stock generator has a compiled cache path and output-directory arguments, with no supported alternate input-directory parameter in the reviewed source. A wrapper that merely chooses another cache path cannot use a documented stock interface. Running stock generation on an unfiltered cache and then deleting foreign units cannot recover units already discarded for `noauto` collisions. [Generator source](https://github.com/openzfs/zfs/blob/master/etc/systemd/system-generators/zfs-mount-generator.c).

## Candidate A: persistent cache per environment

**Inference from the cache contract:** this can be sufficient for host-side mounting if loka writes a complete filtered cache into each environment before declaring it bootable. Its root, selected private members, allowed shared mounts, and external key dependencies must resolve correctly. Clone paths must be rewritten; rename, rollback, and shared-dataset/property changes must refresh affected offline caches too. Old dataset names cannot be treated as enduring identity.

This design requires exclusive cache ownership and a supported policy for changes made outside loka. Disabling stock ZED alone does not provide freshness. Any embedded initramfs cache must also be refreshed or prevented from mounting private members. Direct ZFSBootMenu selection is compatible only after these prerequisites hold for the selected environment. Per-boot initramfs refresh is **not proven universally necessary**, but neither target's current evidence proves that persistent host caches alone are sufficient.

## Candidate B: resolve selection at each boot

**Design candidate:** a root-aware adaptation of the generator resolves the mounted root and constructs eligible input before upstream mount-unit generation. It retains shared mounts and encryption-root metadata, rejects conflicting mountpoints, and preserves explicit requirements for necessary `noauto` members. This needs an implemented selection/input interface; it is not a stock generator feature. A modified generator can emit units directly within the systemd contract, avoiding writes to persistent `/etc` from a wrapper.

Host-side selection can avoid trusting a cloned cache's environment name, but filtering stale rows alone is insufficient: obtaining current names/properties or validating freshness is still necessary. Live inventory is available only for already imported pools; additional shared pools need an explicit metadata/import strategy. Boot-critical mounts before switch-root remain the initramfs's responsibility. This candidate does not require changing stock ZFSBootMenu binaries.

## Common acceptance gates

Both candidates must prevent global `zfs mount -a` from bypassing selection. Both inspected hosts currently enable it; removing its automatic boot path or adopting an equally verified isolation arrangement is required. Cache filtering cannot constrain that command. Musashi's existing explicit mount requirements must remain effective for the selected environment. [Local and remote installation evidence](../boot-environment-installation.md).

Upstream dracut's helper only mounts selected-root descendants with `canmount=on` at certain boot-critical paths, including `/etc` and `/usr`; it does not generally mount every private member. This matches the readable installed helper but does not establish the actual initrd contents. [Upstream dracut helper](https://github.com/openzfs/zfs/blob/master/contrib/dracut/90zfs/zfs-lib.sh.in).

Before certifying either mechanism, verify actual initrd generator/cache inclusion, selected-root mounting, key availability, switch-root ordering, and all other automatic mounting paths. The supplied archive evidence above establishes the observed inclusion boundary; runtime acceptance remains outstanding. Test a directly selected clone with duplicate mountpoints, a renamed environment, rollback with stale embedded configuration, manager reload, and the encrypted shared-ancestor topology. The accepted policy requires a failed private mount to stop normal startup; its implementation must be tested. Floating OpenZFS sources above support feasibility analysis; installed release/source parity and boot testing remain necessary for certification.
